OKF in plain words

The Open Knowledge Format v0.3, explained with examples. It is a reading aid, not a replacement. When this explanation and the spec disagree, the spec is right, and we would like to hear about it.

The bundle

A bundle is a folder. Every Markdown file in it that has a type in its frontmatter is a concept. Subfolders group concepts however you like: the spec does not prescribe a layout, and it does not depend on your domain (§3).

A bundle can be its own git repository, a zip file, or a subfolder of a larger repository. The spec recommends git, because it gives you history and diffs for free. Files and folders whose names start with a dot are not part of the bundle. Non-Markdown files (images, SQL files, scripts) are assets: concepts can link to them, but they are not concepts.

A concept: frontmatter and body

A concept file has two parts. The frontmatter is a YAML block between two --- lines at the very top. The body is everything after it, written in standard Markdown (CommonMark), plus tables and footnotes (§4).

type is the only key that is always required. It is a short label of your choice, such as Table, Metric, Policy or Runbook. There is no official list, and readers must accept types they have never seen. The common optional keys are title, description (one sentence), tags, and resource, a URI for the real thing the concept describes, when there is one.

A body has no required sections. The spec gives a conventional meaning to three headings: # Schema, # Examples and # Computation. Use any other headings you need.

Links and path fields

Concepts point at each other with normal Markdown links, like [customers](customers.md) above. A link says that two concepts are related. The sentence around the link says how. Links that point at a file nobody has written yet are allowed: readers must accept broken links (§6).

Some frontmatter keys hold a path instead of prose. The spec calls them path fields: resource, sources[].resource, superseded_by, and the computation keys. Links and path fields follow the same rule, and both forms below are valid:

Written asResolves fromExample
Starts with /The bundle root/tables/customers.md
Anything elseThe folder of the file that contains itcustomers.md, ../tables/customers.md
Has a schemeNowhere, it is an external URLhttps://wiki.example.com/refunds

The spec does not prefer one in-bundle form over the other. We use the / form for path fields in our own bundles, and say why on Spec and our conventions.

index.md and log.md

Two filenames are reserved at every level of the bundle and are never concepts (§8, §9).

index.md lists what a folder contains, so a person or an agent can see what is there before opening every file. Only the index at the bundle root may have frontmatter, and it describes the bundle as a whole:

log.md is a history of changes, grouped under date headings, newest first. It has no frontmatter, and the date headings must be YYYY-MM-DD.

Optional metadata: source, trust, freshness

When agents write and rewrite most of a bundle, a reader needs a few more answers: where did this come from, who checked it, is it still current. The spec groups the keys that answer these into families (§5). All of them are optional. A concept without them is still valid. It simply tells the reader less.

Provenance: sources

sources lists what a concept was made from. Each entry needs a resource. It can also carry facts about the source, such as its author, when it last changed, and how often it is used. OKF records these facts and leaves the judgment to the reader. To attribute one claim, use a footnote whose label is the source's id.

Trust: generated and verified

generated says who or what wrote the current content, and when. verified lists who confirmed it afterwards. They are kept apart on purpose: the one who writes a concept is often not the one who checks it. Actors are written as human:lena, team:finance-fpa, process:nightly-checks, or agent-name/version for software (§7).

From these two keys a reader works out a trust tier: unverified, machine-confirmed, or human-reviewed. Only a human: actor gives human-reviewed. A team name does not, because it does not say which person looked. In the metric above, the check by team:finance-fpa makes the concept machine-confirmed.

The current-verification rule

A verification counts only if it happened at or after generated.at (§5.3). If an agent rewrites a concept after a person reviewed it, the person has not read the new text, so the concept drops back to a lower tier until someone checks it again. Old verified entries stay in the file as history.

Lifecycle: status, superseded_by, stale_after

status is draft, stable (the default) or deprecated. When a concept is replaced, keep the old file, mark it deprecated and point superseded_by at the replacement. Old links keep working, and a reader looking for current knowledge can follow the pointer (§5.4).

stale_after is a date after which someone should check the content again. Stale does not mean wrong. It means "look at this again". Leave it out when you do not know a sensible review date (§5.5).

Attested computations

Some numbers must be computed one approved way. An Attested Computation is a concept that holds that approved query or script, the parameters an agent may fill in, and a pointer to a checker. After each run, the checker confirms that the approved query is the one that ran (§10). The agent supplies values, never the query. OKF only describes the contract: running it is up to your tools.

A reader must not show a value as attested unless the concept has both a runtime and an attester. Appendix A of the spec has a full worked example with revenue and profit.

Extensions: x- keys

You can add your own keys anywhere in the frontmatter. Readers must not reject keys they do not know, and tools that edit a file must keep them. Future versions of OKF will never define a key that starts with x-, so the spec suggests x-<producer>-<name> for your own, for example x-acme-owner: payments-team (§4.1). okf-skills uses x-okf-skills-upkeep and x-okf-skills-recursive this way.

What conformance means

The spec's definition is short (§11.1). A bundle is conformant when:

  1. every frontmatter block in a .md file parses as a YAML mapping, and
  2. index.md and log.md follow their rules when they are present.

That is all. A Markdown file without frontmatter, such as a README.md, is not a concept and does not make a bundle non-conformant. Most of the rest of the spec is guidance for producers ("SHOULD") and rules for readers ("MUST accept broken links", "MUST NOT reject keys that they do not know"). Readers must not reject a bundle for missing optional fields, unknown types, unknown keys, broken links or missing index files.

How our validator maps to this

Our validator follows this split. Only §11.1 problems are errors. Spec guidance shows up as warnings, and our own style advice is off unless you ask for it with --lint. A README.md inside the bundle and a link to a file that does not exist yet are both warnings, so --strict fails on them. Use --max-warnings if you want to keep them. Passing our validator with extra flags is a choice you make for your bundle, and conformance asks for less. See The toolkit.
