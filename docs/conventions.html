Spec and our conventions

Some habits in okf-skills go beyond what OKF asks for. They are our choices, and they are optional. A bundle that ignores every one of them is still a conformant OKF bundle, and our validator treats it as one.

Side by side

TopicThe spec saysokf-skills doesWhy we chose it
Where the bundle lives Anywhere. A bundle is any folder, a repository, or an archive (§3). Defaults to .okf/ at the repository root. The validator, the visualizer, the MCP server, the Action and the okf skill accept any other path. The Stop hook and the backfill skill only use .okf/. A predictable place lets the skills, the hook and the MCP server find the bundle without configuration. The dot keeps it out of the way of the code.
Path fields A leading / resolves from the bundle root, anything else from the file's folder. Both are valid, neither is preferred (§6). Writes in-bundle path fields such as superseded_by with a leading /. A rooted path still points at the right file after you move the concept that contains it. It also reads the same under v0.2 and v0.3. A bare path does not.
What goes in log.md A history of changes, grouped by date (§9). Records lifecycle events only: a bundle created, a concept deprecated or superseded, concepts regenerated, a verification pass. Routine edits get no entry. git and generated already record every edit. Keeping the log to events that change what is current keeps it short enough to read.
Recommended fields type is the only required key. A concept with only type is fully conformant (§4.1). Suggests title, description, tags and generated, through the validator's --lint flag, which is off by default. They make search, index files and previews better, and they tell a reader who wrote what. They are advice, so they never fail a run unless you ask for them.
Our own keys Custom keys are allowed anywhere. Name them x-<producer>-<name> (§4.1). Uses x-okf-skills-upkeep and x-okf-skills-recursive in the bundle-root index.md to configure the Stop hook. The spec reserves the x- prefix for extensions, so these keys will never clash with a future OKF key. Other tools are free to ignore them.

The okf skill applies these conventions when it writes a bundle. The validator, the visualizer and the MCP server accept both path forms and any bundle location.

Honesty rules for producers

The trust tiers in OKF only mean something if producers fill generated and verified truthfully. The spec defines what the fields mean. These are the rules the okf skill gives an agent so that it uses them honestly:

  • An agent never writes a verified entry for content it generated. Verification is someone else confirming the content. An agent checking its own text is not a check.
  • An agent never invents or guesses a human:<id>. Not from git config, and not from the operating system's user name. It writes human: only when a named person actually wrote or confirmed the content, and the agent was told who.
  • An agent records itself in generated.by as <producer>/<version>, for example claude/opus-5.5.

Put another way: trust is earned by someone checking, not written into the file by the one who wants it. A concept that an agent wrote and nobody checked is unverified. That is accurate, and it is useful for a reader to know.

None of this is part of OKF. Format proposals go to the OKF repository.
