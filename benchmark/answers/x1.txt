QUESTION: Q5
Nothing breaks the run outright, but --strict turns the v0.1-legacy warnings into a failure. The validator treats a v0.1 bundle as conformant: the only hard errors are missing/unparseable frontmatter and a missing type field (§11). The two superseded v0.1 constructs — a top-level timestamp field (now generated: {by, at}) and a body # Citations list (now the sources frontmatter family) — are detected and reported only as warnings, never as errors, per §13.1.
--strict is implemented as max_warn = 0, i.e. "fail if warnings exceed 0". So a bundle that validates cleanly under a plain run will exit 1 under --strict purely because of these legacy-construct warnings, even though it's still spec-conformant.
The way out is --migrate: it rewrites the v0.1 constructs to v0.2 in place, textually (not via re-serializing YAML, to preserve comments/ordering/quoting) — timestamp: X becomes generated with by: process:okf-migrate and at: X, and a # Citations list of markdown links is hoisted into a sources: list. Running the validator with --migrate --strict migrates first, then validates, clearing those warnings so --strict can pass. Note: per-claim attribution (the footnote linking a specific claim to a specific citation) is not recoverable by the migration, and the tool prints a note to that effect.
